# 大写入分批(Large-Write Batching)

大写入以**批次**落地:每个批次一次工具调用、单一职责、几十秒内完成、失败可秒级重试。

为什么:provider 网关会掐断长流(基元律动 GLM-5.3F 实测连续输出 ~4-5 分钟即被 terminated,单次事故烧 50 分钟重试);小批次把重试代价从分钟级压到秒级,并让每次写入可独立审阅。此坑与 provider 无关地成立——小 diff 天然更便宜、更可审。

## 触发

预计单次连续输出超过 ~300 行或 >2 分钟——新文件、大型 Edit、大段重构插入。典型:红测文件、规格实现、长报告、批量配置。

## 序列

1. **切批**:把目标拆成 5-6 个以上批次,每批一个 Edit/Write、单一职责(一个方法/一个章节/一个断言组)。完成标准:批清单落纸,每批独立可编译或可一致性检查。
2. **逐批落地**:每批一次工具调用;该批写入完成即收束本回合输出。完成标准:批内容已在文件中,与既有内容一致。
3. **失败降级**:单批被截断 → 只重试该批(秒级);连续 2 批失败 → 把批次再切一半。
4. **整体自查**:全部批次落地后读一遍完整文件。完成标准:无截断、无重复、无拼接缝;随后照常跑构建/红测。

## 红测场景的批序

锚点方法壳 → 逐断言组 → 注册块。每批落地后照常跑红,批批独立——红测先行与分批正交,互不放松。

## 硬护栏

管道式一次性生成整文件(含"先写完整草稿再修")是本规则要消除的事故形态;整文件内容必须以批次形态落地。

> **本仓库补充(2026-09-08,用户指令)**:实现/TDD 任务硬规则为"每次工具调用一个 Edit(≤60 行)、一次只插一个测试方法、禁止整文件重写";批次之间**自动连续推进,不停等用户确认**(用户不时刻在电脑旁)。归档报告类新建文件不受逐批限制,但仍是单一职责的独立写入。
