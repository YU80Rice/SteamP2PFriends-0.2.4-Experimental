## 2. R31-01：生产分支五段执行可断言

### 2.1 缺陷复述

上一轮（t142）的 seam 允许测试把某段「包装」成记录器，但所有断言都长在 `seam != null` 分支。
审查官把唯一调用点改成 `if (seam != null) a();`（DLL `70b5942b…`）后，生产模式下五段一段都不执行，
而 837/839 仍全绿、Bug2-38 仍 PASS——生产分支零覆盖。

### 2.2 为什么「只在 a() 前后自增」不够

若把计数写成：

```
DiagnosticSectionsEnteredForTest++;
a();
```

则 N2 变异后计数仍是 5（自增语句没有被跳过），Bug2-39 不会红。
因此计数必须与「调用点是否真的执行」绑定，而不是与「函数是否走到这一行」绑定。

### 2.3 落盘改动

文件：`Core/Registration/SteamP2PFriendsPlugin.PatchRegistrationDiagnosticsModules.cs`

- `:129-133` 新增：

  ```csharp
  // R31-01 生产侧计数：每进入一次唯一执行点前自增；用于证明生产分支（seam == null）
  // 五段都真的进入，而不是只验证注入分支。ResetDiagnosticsStageForTest 清零。
  internal static int DiagnosticSectionsEnteredForTest;
  ```

- `:137-141` `ResetDiagnosticsStageForTest()` 增加 `DiagnosticSectionsEnteredForTest = 0;`。

- `:150-163` 唯一执行点改为：

  ```csharp
  // R31-02 测试契约守卫：生产不可达（seam 生产恒 null，a 即真实 action 非空）；
  // 保留它是为了防止测试 seam 返回 null 时静默跳过，令进入计数与真实执行点脱钩。
  if (a == null)
      throw new InvalidOperationException("diagnostic stage action is null for section: " + section);
  // 计数包在唯一调用点的执行体里：a() 真的被调用才计数。
  // 若调用点被改成 if (seam != null) a();，生产模式下计数保持 0（N2 由此变红）。
  Action counted = a;
  a = () =>
  {
      DiagnosticSectionsEnteredForTest++;
      counted();
  };
  a();
  ```

  计数发生在 `a()` 真正执行时；生产模式 `seam == null`，`a` 即真实 action 的包装，
  真实 action 抛异常也会先完成计数，由既有 catch 折成 `ok = false`。

## §9 t155 补记（r10 残余收口）
- 生产分支 wrapper 的「无条件调用」已由 IL 契约钉住：wrapper 零分支 +
  `Action.Invoke` 恰好 1 次且位于计数自增之后；票面建议的
  `CountFieldLoads(..., "DiagnosticStageActionForTest") == 0` 与
  `CountMethodCalls(..., "Action", "Invoke") == 1` 单独不足以抓 M6
  （M6 捕获的是局部 `seam`，被提升为 display-class 字段），故追加零分支断言。
- `DiagnosticSectionsEnteredForTest` 是进程内累计值，任何断言前必须先
  `ResetDiagnosticsStageForTest()`，否则会误红（只会误红，不会把未执行段算成已执行）。
